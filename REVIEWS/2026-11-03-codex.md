## F1 — Old quota windows overwrite current readings during sync

- **Severity:** medium.
- **Location:** `lib/sync.py:77` (grouping and replacement at lines 85–91 and 106–110).
- **What is wrong:** Provider snapshots are merged solely by provider and window name. The merge ignores `stale`, observation age, expired resets, and whether snapshots belong to the same reset cycle. It then copies the maximum reading and its reset into the current row without changing that row's freshness metadata. An offline host's snapshot can therefore persist indefinitely as an apparently current quota. If only that host reports a window, `machines` is 1, which also allows the result through history's multi-machine exclusion.
- **A concrete failure scenario:** A current local Codex weekly window is 10%, resetting at epoch 2000000000. An offline host has a stale 99% snapshot resetting at epoch 100. Calling `merge_rows` produces 99%, reset 100, `machines: 1`, while the row still has `stale: false`. The isolated check reproduced exactly this result. Status/report/watch can show an exhausted old cycle instead of the current 10% cycle.
- **The smallest fix:** Reject stale or expired remote windows, bound freshness for windows without a reset, and compare percentages only within a matching reset cycle. Preserve current local readings when a remote window is ineligible. Add reset-rollover and offline-host tests; the existing sync test at `tests/run.sh:635` covers only matching cycles.

- **Resolution (2026-11-04):** not a bug: the code was removed in 0.12.0 (#13). `lib/sync.py`, `merge_rows`, and `sync_dir` were deleted in `2ca0e82` ("Finish the split"), because Pharos now owns cross-machine data. limitline has no merge left to get wrong. Readings from other Macs come only from Pharos's `usage.json` (`lib/cli.py:96`).
- *History:* before 0.12.0, this was fixed test-first on 2026-11-03 (`sync-expired-remote-ignored`, `sync-old-noreset-ignored`, `sync-other-cycle-ignored`, `sync-stale-remote-ignored`). Those tests were removed together with the code.

## F2 — Nudges recommend a provider whose other window is exhausted

- **Severity:** medium.
- **Location:** `lib/nudge.py:35`.
- **What is wrong:** The nudge ranks each provider by its lowest percentage. A provider is constrained by its most-used active window: a low 5-hour reading cannot compensate for an exhausted weekly window. The status sorter already uses the maximum in `lib/cli.py:57`, so the two views disagree.
- **A concrete failure scenario:** Codex has 5h=1% and 7d=100%; Cursor has an estimated 30%. With no idle-machine hint, `suggestion()` returns `codex 1%`, as reproduced, directing work to an exhausted provider. Existing tests at `tests/run.sh:535` and `tests/run.sh:731` actually require `codex 12%` for a fixture with 5h=12% and 7d=55%, cementing the incorrect choice of window.
- **The smallest fix:** Rank a provider using its highest current window percentage, then choose the provider with the lowest such constraint. Update the current assertions and add a fixture with one exhausted window.

- **Resolution:** fixed in `nudge-exhausted-window` (before the fix: `codex 1%`; after: `cursor ~30% estimate`). Two old assertions required the wrong window, so they were changed on purpose. The old `nudge-codex` is now `nudge-codex-week-constrains`: with 5h 12% and 7d 55%, Codex is not offered as `codex 12%`, and the hint is `→ cursor ok`. A new `nudge-codex` uses a Codex fixture at 30% and 40% and expects `→ codex 40%`. `nudge-v2` now expects `→ codex 40% · mini idle`. `constraint_window` in `lib/nudge.py` takes the maximum, the same rule as `lib/cli.py`'s `constraint`.
- **Rechecked 2026-11-04 against the current `lib/nudge.py`:** this version reads Pharos's `usage.json`, and it still ranks each provider by `constraint_window`, the maximum. Putting the minimum rule back makes `nudge-exhausted-window` fail with `codex 1%`, and `nudge-codex-week-constrains`, `nudge-codex`, and `nudge-v2` fail with `→ codex 12%` and `→ codex 30%`. With the current code all four pass.

## F3 — Resumed Codex sessions disappear because of their original directory date

- **Severity:** medium.
- **Location:** `providers/codex:88`.
- **What is wrong:** Before checking file modification times, the scanner prunes date directories older than its eight-day cutoff. A session created earlier can be resumed and receive fresh quota events in its original rollout file. Directory creation date is not evidence that its contents are old. This also contradicts README's promise to inspect every session file modified in the last eight days (`README.md:302`).
- **A concrete failure scenario:** On November 3, resume a session stored under `sessions/2026/10/01/`; its rollout now contains an event from one minute ago with 50% usage and a future reset. A synthetic file with exactly that state and a fresh mtime returned `source: none`, no observation, and no windows from `read()`. A stale reading elsewhere may win instead, or Codex disappears entirely.
- **The smallest fix:** Remove the directory-date pruning and retain the existing per-file mtime filter. Add a test with a freshly modified rollout inside an older date directory.

- **Resolution:** fixed in `provider-codex-resumed-old-folder` (before the fix: `{"observed_at":null,...,"source":"none",...,"windows":[]}`; after: 5h 50% and 7d 20% from the resumed file). `day_ok` and the folder pruning are removed, and the per-file mtime filter stays. The renderer's Codex segment calls this provider (`scan_codex` runs `providers/codex --fields`), so it is fixed too. `provider-codex-many-files` still skips its old file, now by mtime.
- **Rechecked 2026-11-04:** putting the date-folder pruning back makes `provider-codex-resumed-old-folder` fail again (`"source":"none","windows":[]`). With the current code it passes.

## F4 — Increasing independent Cursor usage events are treated as cumulative totals

- **Severity:** medium.
- **Location:** `providers/cursor:78` (the same heuristic also appears at line 43).
- **What is wrong:** The provider guesses that usage is cumulative whenever successive counts happen to be nondecreasing. Independent request counts can also increase. Their sum is then replaced by only the last count, understating the weekly estimate and affecting routing hints. Ordering alone cannot establish whether a field is cumulative.
- **A concrete failure scenario:** A JSONL log contains two independent objects, `{"usage":{"input_tokens":100,"output_tokens":0}}` followed by the same shape with 200 input tokens. `file_tokens()` returns 200 instead of 300; the isolated check reproduced this. Against a configured 1000-token budget, the displayed estimate becomes 20% instead of 30%.
- **The smallest fix:** Sum independent `usage` events by default; use a last-total policy only for a schema or source explicitly known to contain cumulative counters. Remove the corresponding monotonicity guess from nested usage extraction and test increasing per-request events as well as explicitly cumulative records.

- **Resolution:** fixed in `cursor-rising-events-summed` (before the fix: `200 20`; after: `300 30`) and in `cursor-nested-usage-summed` for the nested heuristic at line 43 (before: 70; after: 120). Both monotonicity guesses are removed. A `usage` object marked `"cumulative": true` is the only one treated as a running total, so only its last value counts (`cursor-cumulative-last-total`, 250). The shipped fixture has one record, so `provider-cursor-estimate` and the `~11%` tests are unchanged.
- **Rechecked 2026-11-04:** putting the line-level monotonic guess back makes `cursor-rising-events-summed` fail again (`200 20`). With the current code it passes.

## F5 — Configured sync works for the renderer but is ignored by status/report/watch

- **Severity:** medium.
- **Location:** `lib/cli.py:97`.
- **What is wrong:** `prepare()` reads only `LIMITLINE_SYNC_DIR`, whereas the renderer and background cockpit publisher also read `sync_dir` from the configuration file. README documents either configuration method for status, report, and watch (`README.md:370`). The commands silently skip publication and merging when users follow the config-file method.
- **A concrete failure scenario:** Put `sync_dir = "/some/shared/folder"` in the selected `config.toml`, leave `LIMITLINE_SYNC_DIR` unset, and provide another machine's quota snapshot there. `limitline status`, `report`, and `watch` show only local quotas and do not publish their provider rows, although background cockpit synchronization uses that same configured folder. An isolated `prepare()` check confirmed that the configured destination was never created.
- **The smallest fix:** Resolve the setting through `config.setting("sync_dir", "LIMITLINE_SYNC_DIR", "")` in `prepare()`. Exercise both config-file and environment configuration in the sync tests; the current test at `tests/run.sh:636` sets only the environment variable.

- **Resolution (2026-11-04):** not a bug: the code was removed in 0.12.0 (#13). `sync_dir` and `LIMITLINE_SYNC_DIR` no longer exist. `prepare()` no longer publishes or merges anything (`lib/cli.py:96`). `limitline doctor` reports an old `sync_dir` key as "removed; other Macs come through Pharos" (`lib/cli.py:440`, `doctor-obsolete-keys`). The README says earlier `sync_dir` settings are ignored (`README.md:413`).
- *History:* before 0.12.0, this was fixed test-first on 2026-11-03 in `sync-config-file`. That test was removed together with the code.
